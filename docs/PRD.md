# PRD — 느린 기차 (slow_train)

> 제품 기획서 (Product Requirements Document)
> 상태: **싱글플레이 베타 · 멀티플레이 기획 완료** · 최종 갱신: 2026-11-17

---

## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | 느린 기차 (slow_train) |
| 장르 | 3D 힐링 소셜 웹게임 |
| 개발 방식 | 1인 기획 + AI 보조 개발 (Claude Code, ChatGPT) |

**콘셉트**
옛 무궁화호의 감성을 담은 온라인 기차 여행 공간.
이용자는 기차에 탑승해 창밖 풍경을 감상하고, 다른 승객과 간단한 말풍선으로 소통하며, 간식을 구매하는 등 느긋한 기차 여행을 경험한다.
경쟁이나 승패보다는 편안한 분위기와 소소한 상호작용을 중요하게 생각한다.

---

## 2. 기획 의도 / 목적

| 구분 | 내용 |
| --- | --- |
| 문제의식 | 경쟁·성과 중심의 게임/서비스가 많아, "아무것도 안 해도 되는" 쉼의 경험이 드물다 |
| 목표 | 설치 없이 브라우저에서 바로 즐기는 **느리고 편안한 경험** 제공 |
| 핵심 가치 | 힐링 · 향수(무궁화호) · 가벼운 사회적 존재감(다른 승객) |
| 장기 방향 | 실제 이용자가 함께 타는 **메타버스형 기차**로 확장 (현재는 NPC로 대체) |
| 개인 목표 | 상용화 가능한 서비스 수준으로 보안·최적화·접근성을 갖춘 개인 프로젝트 |

## 3. 타깃 사용자

- 짧은 시간에 가볍게 쉬고 싶은 사용자 (PC/모바일 모두)
- 레트로·기차 감성을 좋아하는 사용자
- 한국어 사용자 (현재 UI는 한국어 전용)

## 4. 핵심 원칙

1. **정직한 표시** — 구현되지 않은 기능을 완성된 것처럼 보이지 않는다.
2. **NPC 구분** — 베타 승객은 이름표에 "베타"를 붙여 실제 이용자와 구분한다.
3. **결제 없음** — 승차권·간식 구매는 모두 가상이며 실제 결제는 일절 없다.
4. **외부 에셋 없음** — 모든 3D 모델은 코드로 만든 도형 (라이선스 이슈 최소화).
5. **모바일 우선 확인** — 가로(PC)/세로(모바일) 모두 자연스러워야 한다.

## 5. 기술 스택

### 현재 사용

| 기술 | 역할 |
| --- | --- |
| HTML / CSS | 마크업 및 UI 스타일 |
| Vanilla JavaScript | 게임 로직 전체 |
| Three.js r128 | 3D 렌더링 (CDN 로드) |
| Vite | 로컬 개발 서버, 빌드 |

### 향후 도입 예정

| 기술 | 역할 |
| --- | --- |
| Supabase | 사용자 인증, 프로필/승차권 저장, 멀티플레이 상태 관리 |
| Supabase Realtime | 객차별 실시간 위치·착석·말풍선 동기화 |
| Netlify (또는 동급 서비스) | 웹 배포 |

### React 미사용 결정

React는 현재 프로젝트에서 사용하지 않기로 결정했다.

**이유**: Three.js 중심의 3D 게임으로, 현재 규모에서는 Vanilla JavaScript만으로도 구현이 가능하다.
React를 도입하면 Three.js 렌더 루프와 React 렌더 사이클을 조율하는 복잡성이 추가된다.

## 7. 사용자 경험 (UX 흐름)

```
시작 화면(승차권 모양)
  └ 닉네임 입력 → [승차권 사고 탑승] / [무임승차로 탑승]
        ↓
객차 탑승 (컷어웨이 3D, 천천히 흐르는 창밖 풍경, 임시 기차 소리)
  ├ 이동 · 착석 · 말풍선
  ├ 간식 판매원 → 가까이 가서 [말걸기] → 가상 구매 → 손에 듦
  ├ 승무원 검표 → 표 보여주기 ✔ / 표 없음 → 5초 후 강제 퇴장
  └ 의자 틈 발견 → 숨기 (승무원 검표 회피)
```

## 9. 멀티플레이 기획

> 상태: **기획 완료** · Supabase 미연결

### 9.1 객차 Room 구조

- 1객차 = Supabase Realtime 채널 1개
- 객차당 총 32석
- 실제 이용자 정원: 초기 최대 24명
- NPC는 이용자 정원에서 제외, 최대 5명에서 시작
- NPC는 실제 이용자 증가 시 슬롯 양보

### 9.2 객차 입장 흐름

```
최초 접속
  └ 빈자리 있는 객차 자동 배정 (가능하면 승객 많은 쪽 우선)
        ↓
객차 탑승 → 승차권 발급 (객차 번호 + 지정 좌석)
  └ 게임 내 객차 목록에서 다른 객차 선택 가능
      ├ 빈자리 있음 → 이동 (기존 승차권 반환 → 새 승차권 발급)
      └ 만석 → 입장 불가
```

### 9.3 실시간 동기화 대상

| 항목 | 방향 |
| --- | --- |
| 이용자 입장/퇴장 | 서버 → 전체 |
| 위치 · 이동 방향 | 클라이언트 → 서버 → 같은 객차 전체 |
| 착석 / 일어나기 | 클라이언트 → 서버 → 같은 객차 전체 |
| 말풍선 | 클라이언트 → 서버 → 같은 객차 전체 |
| 객차별 접속 인원 | 서버 → 전체 |
| NPC 상태 | 서버 주도 또는 호스트 클라이언트 중계 (미결정) |

### 9.4 동시 착석 충돌 처리

동시에 같은 좌석을 선택하는 경우는 서버 측에서 권한을 확인한 후 처리한다.
클라이언트는 서버 응답 전까지 임시 착석 상태를 허용하고, 충돌 발생 시 서버 결과를 최종 적용한다.

### 9.5 현재 구현 상태 (Supabase 연결 전 준비 완료)

- `GameState.carId` — 객차 번호 보관 (현재 단일 값 1)
- `GameState.occ` — 객차별 좌석 점유 테이블 (객차 이동 시 초기화 대상)
- `actorSnapshot(a)` — 서버 전송용 직렬화: `{ id, name, carId, x, z, ry, state, seatId, nookId }`
- `applyActorSnapshot(a, snap)` — 서버 수신 상태 행위자에 적용
- `Repo` 인터페이스 — `SupabaseRepo`로 한 줄 교체 가능

## 10. 승차권 및 좌석 시스템

> 상태: **기획 완료** · 미구현

### 10.1 좌석 구성 (총 32석)

| 구분 | seatType | 개수 | 위치 | 비고 |
| --- | --- | --- | --- | --- |
| 일반 지정석 | `'reserved'` | 24석 | 창가 2인 벤치 양쪽 각 6줄 | 승차권 발급 대상 |
| 중앙 테이블 자유석 | `'free'` | 8석 | 중앙 4인 테이블 2개 | 승차권 미발급 |

### 10.2 지정석 운영 규칙

- 최초 탑승 시 객차 번호와 지정 좌석이 표시된 승차권 자동 발급
- 승객은 발급받은 지정석을 찾아가 앉을 수 있다
- 다른 승객의 지정석이 비어 있다면 임시 착석 가능
- 지정석 소유자가 자리 반환을 요청하면 임시 착석자는 반드시 양보해야 한다
- 반환 처리는 서버에서 소유자 권한을 확인한 후 적용한다

### 10.3 자유석 운영 규칙

- 중앙의 마주 보는 4인석 테이블 2개를 자유석으로 운영
- 자유석에는 지정 승차권을 발급하지 않는다
- 누구나 빈자리에 착석 가능 (선착순)
- 자유석에는 다른 승객의 반환 요청 기능이 적용되지 않는다
- 동시 착석 방지는 `GameState.occ`로 관리

### 10.4 좌석 상태 데이터 모델

```js
// 현재 (싱글플레이 베타)
GameState.occ[seatId] = actorId   // 착석자 ID

// 향후 (멀티플레이 + 승차권 시스템)
GameState.occ[seatId] = {
  reservedBy:  userId | null,   // 승차권 소유자 (지정석만, 자유석은 null)
  occupiedBy:  actorId | null,  // 현재 착석자
}
```

SEATS 데이터의 `seatType` 필드(`'reserved'` / `'free'`)는 현재 코드에 반영되어 있다.

### 10.5 객차 이동 시 처리 흐름

```
객차 이동 요청
  └ 기존 승차권 반환 (Repo.returnTicket)
  └ GameState.occ = {}  (좌석 점유 초기화)
  └ GameState.carId = newCarId
  └ 새 객차 승차권 발급 (Repo.issueTicket)
```

| 성능 | 모바일에서도 부드럽게. 픽셀 비율 최대 2, 말풍선·텍스처 사용 후 `dispose` |
| 보안 | 외부 입력은 신뢰하지 않는다. 서버 연동 시 인증·권한·입력 검증 필수 |
| 접근성 | 키보드 조작, 포커스 표시(`:focus-visible`), 다크모드 대응. 팝업 접근성은 개선 예정 |
| 호환성 | 최신 크롬/사파리/엣지, iOS·Android 브라우저, WebGL 필요 |
| 유지보수 | 모든 함수/블록에 한글 주석, 기능별 파일 분리 |

## 13. 기술 제약

- ES 모듈 미사용 — `file://`로도 실행 가능하도록 일반 `<script>` 로드 방식 유지
- Three.js r128 (cdnjs) + OrbitControls (jsdelivr 0.128.0) — CDN 로드
- 저장소는 `Repo` 어댑터로 분리 — `SupabaseRepo`로 한 줄 교체 가능
- Vite 사용 — 로컬 개발 서버 및 빌드만 담당, 번들링은 비모듈 스크립트 특성상 미적용

## 16. 개발 및 기록 원칙

### 16.1 AI 보조 개발 방식

이 프로젝트는 사용자 1인이 기획·의사결정을 담당하고, AI가 구현을 보조하는 방식으로 진행한다.

| 역할 | 담당 |
| --- | --- |
| 아이디어, 요구사항, UX 기획, 기능 선택, 테스트 및 최종 의사결정 | 사용자 |
| 코드 생성, 구현, 리팩터링, 오류 수정 | Claude Code |
| 기획 논의, 기술 선택 검토, 개발 방향 및 요구사항 정리 | ChatGPT |

### 16.2 문서 기록 원칙

- **상태 구분 필수**: 기획 완료 / 구현 중 / 구현 완료 / 테스트 완료
- **정직한 기록**: 실제로 구현하거나 테스트하지 않은 기능을 완료로 기록하지 않는다
- **DEVLOG**: 실제 코드 변경이 발생했을 때만 기록한다
- **PRD**: 기획이 확정되면 반영하되, 구현 여부는 상태 태그로 명시한다
- **PROMPTS**: 주요 의사결정과 프롬프트를 기록해 의도와 결과를 추적한다
